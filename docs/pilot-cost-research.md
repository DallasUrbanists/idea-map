# Pilot environment, identity and cost plan

Status: planning baseline incorporating maintainer decisions, 2026-10-31; implementation details remain subject to validation. This document configures nothing. The provisional target is **$50 per month in aggregate**, not a spending cap or price quote. Local/development and production are separate; v1 resources and data remain untouched. Resource names below are examples, subject to availability and organization naming rules.

## Environment inventory and isolation

| Resource | Local / development | Production |
| --- | --- | --- |
| Google/Firebase project | `idea-map-dev` (local emulators by default; isolated cloud dev only when needed) | `idea-map-prod` |
| Hosting / Cloud Run | dev site and `idea-map-web-dev`, `idea-map-worker-dev` | prod site and `idea-map-web-prod`, `idea-map-worker-prod` |
| PostgreSQL/PostGIS | local container with synthetic fixtures; separate Neon `idea-map-dev` project when integration needs it | separate Neon `idea-map-prod` project and database |
| Firestore | local emulator; separate dev default database | prod default database for projections |
| Tasks / Scheduler | local fake or `idea-map-dev-queue` and dev repair job | `idea-map-prod-queue` and prod repair job |
| Media / backup | `idea-map-dev-uploads`, `idea-map-dev-public`, `idea-map-dev-backups` | corresponding `idea-map-prod-*` buckets, globally unique names to be confirmed |
| Secrets and providers | dev-only Secret Manager secrets, Neon role, Resend key/domain and restricted Maps keys; Gemini disabled pending review | distinct prod secrets, Neon roles, sending domain and provider keys |

Dev contains synthetic data only; do not copy production personal data, credentials or backups into dev. Use separate Firebase Auth tenants/projects, application origins and OAuth redirect allowlists. Separate projects provide a boundary for IAM, quotas and Firestore's default-database free allowance; shared billing accounts still aggregate some allowances. Prod uploads and backups are private, with approved previews in a separate public bucket. Use short-lived signed uploads scoped to an object, size and expiry; never make pending media public. Encrypt at rest and restrict backup access. The pilot recovery objectives are at most 24 hours of data loss and 24 hours of downtime. Before launch, verify the backup method and rehearse a restore into an isolated clean environment against both targets; document the recovery operator. Start with seven daily backups, review retention against recovery objectives and privacy obligations, and account for soft-deleted versions as storage. No production data in CI logs, fixtures or local machines.

## Identities and access proposal

- Separate Cloud Run service accounts `web-{env}` and `worker-{env}`. Grant each access only to its required secrets and resources in its own project. Web may read approved public objects and create tightly scoped signed uploads; worker may process pending objects, publish approved previews, enqueue necessary tasks and send mail. Neither receives project Owner, billing administration, IAM administration, broad secret access or backup deletion. Design custom roles where predefined roles exceed the required operations; verify API permissions in implementation.
- Use distinct least-privilege database roles: web has only the tables and operations needed for authorized requests; worker has only its job operations; a separate migration role owns schema changes. Runtime uses pooled TLS connections; migration uses a direct connection. Store connection credentials and provider secrets in per-environment Secret Manager with only the consuming identity able to access each secret version. Rotate and audit them; do not embed secrets in browser bundles or commit them.
- Cloud Tasks invokes the worker using a dedicated invoker service account with `run.invoker` on that service only. Scheduler uses a separate invoker identity for the repair endpoint. Authenticate and authorize the audience, and make job handlers idempotent; neither identity can deploy or change IAM.
- GitHub Actions uses OIDC and [Workload Identity Federation](https://cloud.google.com/iam/docs/workload-identity-federation-with-deployment-pipelines) with conditions on the immutable organization/repository IDs, approved workflow and protected ref/environment. Use separate dev and production deploy identities, with production environment approval and reviewed changes. Prefer direct federated resource access; impersonate a dedicated deploy service account only where needed. Grant build registry write only to the relevant repository and deployment rights only on the target services; narrowly grant `iam.serviceAccounts.actAs` for the corresponding runtime identity. Build, deploy, migration and infrastructure administration are distinct responsibilities. Never issue long-lived service-account keys. Infrastructure/IAM changes require a separately reviewed plan and privileged human-controlled identity.
- Developers use individual short-lived credentials for dev only, and production access is limited to named maintainers with audited, time-limited access. Browser Maps keys are public identifiers, not secrets: restrict by allowed HTTP referrers and APIs, with a separate server key restricted to its required APIs and environment.

## Regions and network

Prefer `us-central1` for Cloud Run, Firestore, Tasks, Scheduler and regional storage where supported. Firebase Hosting serves through a global CDN; its edge is not a selectable `us-central1` service. Gemini Developer API, Resend and Maps are provider-managed endpoints; verify their data handling and regional terms before sending user content. Neon runs on a different provider and cannot be assumed to be co-located in Google Iowa. Recommend evaluating Neon AWS `us-east-2` (Ohio) as a candidate, subject to current availability and plan; [Neon's latency dashboard](https://neon.com/demos/regional-latency) lists that region. Measure warm and cold end-to-end latency and database resume with realistic traffic, including cross-cloud round trips; select the nearest acceptable available region based on measurements, resilience and data residency. Cross-cloud traffic may incur egress, including backups and large queries. Use pooled connections, bounded result sizes and caching, and verify both providers' current transfer charges. Do not promise a latency or cost based on geography alone.

This leaves $19.73 against the target, but neither the $2 allowance nor $10 contingency is a priced ceiling. Storage operations and egress, logging, Secret Manager, registry, backups, support, taxes, identity providers and separate dev usage can exceed them. The model assumes eligible Neon Free usage, no minimum instances and no additional Maps SKUs; Gemini is disabled. Neon Free's published 6-hour restore window is insufficient as the sole daily recovery plan; validate separate backup/restore, and price any enhanced history or paid dev usage. Resend Pro adds $20/month for 50,000 emails and removes the daily limit; that alone raises this example to $50.27, before additional usage. A continuously awake 0.25 CU Neon compute for 730 hours is 182.5 CU-hours, exceeding the assumed Free compute allowance; confirm current limits and price a suitable paid plan before relying on that workload. Another 10,000 Dynamic Maps loads adds $70 at the listed first paid tier. A $50 target is therefore plausible only with measured low traffic and active operational review, not assured.

Firestore fan-out example: 1,000 updates/day to a document watched by 20 clients produces approximately 20,000 listener reads/day, before initial queries, reconnects, index reads and other traffic; add these to the 30,000 assumption, not just the 1,000 writes. Daily free quota resets and uneven peaks mean monthly averages alone cannot prove $0. Named databases do not receive the free quota. Validate actual listener behavior and daily metrics.

## Controls, alerts and response

Propose one Google Cloud alerts-only monthly budget scoped to both v2 projects and all Google Cloud services at $50, with actual-spend thresholds 50%, 80% and 100% ($25, $40, $50). Use a shared billing account for the separately reportable dev and production projects, subject to verifying that reporting. Billing owner: Hexel Colorado (hexel@dallasurbanists.org); the backup is unassigned and must be named before production. Route notifications to the owner and, once named, the backup; review forecast alerts and billing exports. They can lag and **do not stop usage**. Google billing covers only charges in its scope; it does not aggregate Neon or Resend invoices, and the Gemini Developer API billing arrangement must be verified separately. Track Neon usage and Resend plan/usage in their consoles, record their invoices plus any separately billed Gemini charges in a shared monthly ledger, and compare the combined total and forecast against the same $25/$40/$50 thresholds. Assign an owner to review at least weekly and daily near thresholds. These are proposed manual aggregate alerts, not configured automated cross-provider alerts.

At $25 investigate trend and outliers; at $40 reduce optional AI, map and media traffic and prepare a maintainer decision; at $50 escalate and decide whether to suspend optional features or accept additional spend. Never automatically disable billing or delete data: service interruption and recovery need an explicit operational decision. Provider quotas, rate limits and max instances reduce exposure but can be exceeded by billing lag, retries, shared accounts or other SKUs and may affect availability. Start with zero minimum Cloud Run instances, a proposed maximum of 2 web and 1 worker instances per environment, concurrency 20 web / 1 worker and a bounded database pool; load-test and adjust before launch. Restrict Maps APIs and set per-SKU quotas, daily application limits and abuse protections; keep Gemini disabled until its use, data handling, current terms and expected cost are reviewed; if later enabled, set token/request limits and review grounding; cap uploads and size, retention, queue retry rates, and email volume. Cache only approved anonymous content; private responses remain `private, no-store`. Quotas are not equivalent to a dollar cap.

## Decisions before implementation

1. **Billing and ownership:** confirm shared-account cost reporting and existing usage that consumes free allowances; name a backup billing owner before production.
2. **Neon placement and recovery:** benchmark Ohio against other available regions from Iowa; verify Free eligibility and separately priced backup/restore against the 24-hour data-loss and downtime objectives. Rehearse restore before launch, document the operator, and confirm backup retention and cross-cloud transfer costs. Revisit a paid plan if needed.
3. **Provider privacy and availability:** Gemini remains disabled until its specific use, data handling, current terms and expected cost are reviewed. Verify data processing, residency and retention for each provider; confirm Resend daily headroom and separate sending domains, and review Maps SKU selection and restrictions.
4. **Operational envelope:** agree on actual traffic, workload duration, daily peaks, max instances, concurrency, database pool, listener counts and retention after pilot measurements. Recalculate all rows and reserve; approve service degradation and manual response owners before production.

References above are provider documentation; this is a planning snapshot and must be repriced before committing funds. Implementation, billing activation, permissions, credential creation and live provider smoke tests belong to later reviewed work.
